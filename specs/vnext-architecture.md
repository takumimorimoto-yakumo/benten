## 2. Deployment and dependency architecture

Keep the Node 24/pnpm 10 monorepo and current `packages/registry`, `packages/mcp`, `packages/solana`; do **not** retain Next.js as the destination Web framework. The recommended deployment has **three independently built units**: `apps/public-web` owns React Router v7/Vite static HTML/.data, page ingress and the future isolated wallet client; `apps/public-api` owns only snapshot-backed fact JSON; `apps/acquisition-bff` owns quote/evidence and separately scoped purchase-context consumers. Web routes `/api/acquisition/**` to the fixed BFF origin and remaining `/api/**` to facts; neither target is caller-controlled. BFF/owner failure cannot remove facts. Web imports neither server app; BFF imports neither snapshots nor DEX SDK. `packages/mcp` remains local stdio. No facts or server order DB is added. Shared TTL state contains only session/admission data. Browser never receives a service/provider token; audited unsigned bytes appear only in the purchase-ready branch, while signed bytes never leave the browser. No current connector exists; the current Next app remains until an authorized safe cutover.

### C-WEB: URLs, generated output, and host HTTP behavior

`apps/public-web/react-router.config.ts` derives paths from the validated registry, **not** an external runtime request or hand-maintained ticker list. Generate canonical English `/`, `/stock/{TICKER}` and `/{locale}`, `/{locale}/stock/{TICKER}` for `ja`, `ko`, `zh-Hans`, `zh-Hant`: currently 5 Homes + `154 × 5 = 770` details, 775 document URLs before sitemap/404. That count is computed from the reviewed registry, not hardcoded as a permanent market size. `app/routes.ts` maps these to `routes/home.tsx` and `routes/stock.tsx`; client navigation must require `ticker === resolveTicker(ticker).ticker` and an exact supported locale before rendering. For a known casing alias such as `/stock/nvda`, the ingress first resolves the exact allowlist and issues a same-origin **308 redirect** to `/stock/NVDA`, preserving query; the client route canonicalizes navigation to that same URL rather than rendering a case-mismatched dossier. Malformed/unknown, encoded slash, trim-changing and double-decoding cases fail 404; validated percent-encoded aliases and trailing slash behavior are F0 golden tests. API ticker selector normalization remains unchanged. English `/en` and its detail paths are deliberately invalid. All entries may have different financial coverage; no-data pages still render truthful identity/coverage. Prerender `true` alone is insufficient for dynamic paths. Static build must fail if registry resolution, route enumeration, generated `.html`/`.data` pair, locale metadata or registry-derived expected count diverges. Exact output paths/trailing slash are F0 measurements, not assumptions. Route `meta` produces unique locale title/description, canonical and alternate/hreflang, and token-versus-underlying wording at build time; generate sitemap/robots from the same list. Wallet/RPC imports and full financial snapshots must not enter the discovery client bundle; build-only loaders obtain DTOs from the registry and serialize only public projection. Hydration/navigation must preserve the prerendered meaning; the new UI renders verified facts or a clear no-verified-fact state, never legacy values as verified facts.

The [selected-tracks implementation plan](stocklana-selected-tracks-implementation-plan.md) adds catalog/company/provider-market/DBC route families from a separately reviewed `provider-assets.v1.json`. Their paths use an additive manifest with its own revision and never change the 775 xStock baseline or registry. Static initial views use only reviewed artifacts; selecting explicit evidence refresh is the first point that creates an acquisition session/BFF request. Build/release checks bind both manifest revisions and reject missing, extra or live-discovered routes.

The **Web Project ingress**, not either JSON runtime, owns this exact order: **`/api/acquisition/**` -> fixed reviewed acquisition-BFF origin; all remaining `/api/**` -> fixed reviewed facts API origin; generated assets/known HTML/data -> immutable Web static files; remaining known-casing aliases -> validated canonical 308; all other requests -> locale-aware actual HTTP 404**. Both API rewrites preserve full path/query and forward only deployment-controlled Host/forwarded-host metadata; the BFF independently validates its allowed proxy host and exact browser Origin. Acquisition-session Cookie, CSRF and nonce headers are forwarded only to the BFF and stripped before facts/logs. Its direct origin is browser-CORS closed. Unknown acquisition path/method is a BFF JSON 404/405 and never falls through. BFF outage leaves facts/static reachable. Purchase context is dynamic and exact-mint only; no static acquisition page or generic context route is generated. Only the later reviewed isolated browser feature may invoke the wallet and fixed RPC after consuming the audited context; the BFF never signs or submits. Existing host 404/308/cache/skew requirements remain unchanged.

### C-API/MCP: exact public transport parity

The **API Project** owns only current `GET /api/v2/fundamentals`, `GET /api/v2/financials`, `GET /api/fundamentals/:ticker`, `GET /api/financials/:ticker`; known-path methods follow the compatibility matrix below; unknown API paths use a separately specified JSON 404 transport behavior. Recommend a pinned Hono 4.x shell (`hono@4.13.7` and optional standalone `@hono/node-server@2.1.1` were registry-metadata candidates on 2026-09-14, **not installed/build-verified**). [Official Hono Vercel guidance](https://hono.dev/docs/getting-started/vercel) shows `src/index.ts` exporting the app as default for zero-config detection; F0 proves this exact app/root/build output. A native Vercel Fetch entry is a separately proved fallback if strict host parity fails, not an invented Node bridge. Hono handles route/method/error plumbing, not financial semantics. Port the current [Next handlers](../apps/web/app/api/) and presenters without `NextResponse`; never use React Router `action`/resource routes for JSON business APIs. Preserve v2 `schema_version: "2.0"`, `artifact_revision`, `release_profile`, `data`, `disclaimer`; raw `URLSearchParams` strict unknown/repeated query rejection, exactly one ticker/mint, malformed-vs-unknown mint and selector-before-statement precedence. Do **not** use Hono's parsed `query()` if it discards duplicates; its automatic HEAD behavior must be compared to the current host oracle. Preserve 200 success/not-eligible/no-data, 400 invalid, 404 unknown, 503 unavailable and legacy v1 body/status/aliases as **golden behavior**, including unusual no-data semantics. JSON data/error responses retain the public disclaimer; bodyless method-control responses follow the matrix below. MCP's malformed-input echo in structured/legacy text is an intentional transport exception, not duplicated financial logic. `packages/registry` is semantic SSOT; API and MCP remain separate presenters, and Web initial HTML consumes a build-only public projection rather than importing the API runtime. Handler-level timeout returns the existing `service_unavailable` JSON envelope; host-level proxy/functions errors may be non-JSON and Web treats them as unavailable, never facts. Public GET uses bounded request size and rate limits **at the direct API origin as well as Web ingress**, because a caller can bypass the proxy. Initial direct-origin browser CORS is closed, and there is no private financial/RPC/DEX import, HTML 404, static asset serving or unaudited health endpoint. Monitor readiness by a specified known GET/status/revision without leaking user data; any distinct ops endpoint requires a separate versioned contract. Both origins have independent logs and rollback evidence.

For the four **known** legacy/v2 paths, freeze a Next-independent golden method matrix in `apps/public-api/tests/golden/**` **before** N0 removes the old app. The installed local Next route-module behavior is evidence, not proof of a deployed host:

| Method on a known path | Target status/body/header behavior | Compatibility claim |
| --- | --- | --- |
| `GET` | Existing v1/v2 selector-specific 200/400/404/503 JSON envelope and headers | Exact current API oracle, all 154 and malformed inputs. |
| `HEAD` | Same selector-derived status and material response headers as `GET`, **empty body** | Next auto-HEAD behavior; capture local and later host golden cases. |
| `OPTIONS` | `204`, **empty body**, `Allow: GET, HEAD, OPTIONS`; no unsolicited browser CORS grant | Existing installed Next auto-method behavior; explicit Hono handler, not default inference. |

| Unknown `/api/**` path, **any** method including `OPTIONS` | New `404`; all except `HEAD` return `Content-Type: application/json`, `Cache-Control: no-store` and `{"error":{"code":"unknown_endpoint"},"disclaimer":PUBLIC_DISCLAIMER}`; `HEAD` returns the same status/material headers but empty body. ### C-RELEASE: independent code deployments, coordinated public artifact data

Web and API are **separate code release units**. A backward-compatible Web-only or API-only code change can deploy independently while both still use public artifact revision `R`. This is operational independence, not a promise that two Vercel Projects change aliases atomically. A four-file public-artifact update produces reviewed `Rnew` builds/previews for **both** Projects and passes each Project's direct-origin/static/contract tests before promotion. Recommended order: promote API `Rnew`, then Web `Rnew`; the old Web still displays its labeled static facts at `Rold`, but a browser page with `Rpage` must compare every dynamic v2 response's `artifact_revision` to `Rpage` **before** use/cache. If unequal, discard the entire dynamic result, show a five-locale “data update in progress; page facts are revision Rpage” state with manual retry/reload, and never merge old/new fields or say current. Cache keys include artifact revision and selector; mismatched responses are not cached as usable facts. API outage likewise leaves static browse/detail facts visible and dynamic panels unavailable. If API promotion fails, do not promote Web; if Web promotion fails or the mismatch persists beyond a **recommended 10-minute maximum monitored window**, restore the previous attested API deployment while old Web remains, or serve a static maintenance state if no safe pair exists. After both promote, compare direct API and Web-proxied response revisions, real HTTP statuses and a sample of prerendered pages. Roll back an unsafe new pair in the reverse order with the same fail-closed mismatch behavior, using separately attested Project deployments; [Vercel instant rollback](https://vercel.com/docs/instant-rollback) is per Project and does **not** prove a cross-Project atomic restore or a custom alias change. These are proposed release steps and timebox, not executed host proof. If zero mixed-revision window becomes a hard requirement, a version-selected API or shared gateway release pointer needs a **new reviewed architecture and cost decision**; the initial plan adds neither multi-version artifact storage nor another gateway service. The user-visible invariant is **no mixed-version facts within one page and no hidden staleness**, not that every static page always equals the latest API artifact during a staged update. The existing [four-file release](../docs/snapshot-release.md) stays atomic as an artifact set with strict schema/hash/count/source checks and dedicated artifact commits. Cache static documents/assets by deployment/revision; API dynamic responses start with `Cache-Control: no-store` through both direct origin and proxy until proven otherwise, because [Vercel external rewrites](https://vercel.com/docs/routing/rewrites) may respect upstream cache headers. Expose source period/date and revision per verified fact; no marketing freshness shorthand or undocumented private fallback.

Web **deployment skew is a second dimension**: a code-only Web deployment can keep the same `artifact_revision` while changing route modules, `.data`, JS and CSS. Generate a public opaque `web_release_id` from the reviewed Web build/deployment and include both IDs in every HTML page and every build-time root/leaf `.data` payload. A no-store same-origin `/_web-release.json` marker advertises the active Web deployment, but a preliminary marker fetch alone is subject to a cutover race and is **never** the safety check. Before consuming or caching any navigated/revalidated/prefetched `.data` or root/leaf combination, a common Web guard requires all known `web_release_id` and `artifact_revision` fields to equal the current document; missing/unknown IDs also fail closed. If React Router v7 offers no provable pre-consumption hook for *all* these paths, disable client-side data-bearing navigation/revalidation/prefetch and use native full-document navigation instead; F0-W must prove this fallback actually prevents partial data merges, not merely declare it. Never rely on automatic Vercel skew protection for React Router without provider evidence. On `pageshow` (including Back/bfcache), visibility regain, pre-navigation, and loader/chunk error, compare the current marker, discard cached financial data and request a same-URL hard document reload if the Web release differs or a resource is untrustworthy. Preserve safe query/filter/locale URL state, but not old financial cache. At most **one automatic reload per target release and URL per tab** is permitted; unavailable storage, repeated missing chunk/manifest, or a second failure shows a localized manual-reload/unavailable state rather than looping. A marker/network outage keeps labeled static facts but disables dynamic joins/navigation that cannot be validated. F0-W proves the guard/hook or the full-navigation fallback and hashed old/new route-manifest/JS/CSS behavior locally; S0 owns its implementation, R0 tests an old open tab through code-only and data promotion **and rollback**, cached prefetch, Back/locale navigation, missing old chunks and host cache behavior. This is a proposed contract, not verified framework or provider behavior.

## 3. Acquisition context and legal boundary: future only

They are **future proposals**, not deployed routes or an override of the current v1/v2/snapshot-only API. Its A3/A4/A5 feasibility and audit work refines this plan's X0/X1; its owner-direct transport gate refines P0; optional X2 needs a separate browser/session or remote-tool decision without creating a Benten signing/submission path.

`no_verified_pool` means Benten has not reviewed a route, not that no market exists. The **size-independent GET** route capability is a typed, versioned union separate from registry coverage: `not_reviewed | pool_verified_only | quote_unavailable | temporarily_unavailable | disabled_by_policy`; an unreviewed mint has no invented pool/program/slot fields. A later **owner- and size-bound POST** may return `quote_context_ready` only for a released, legally reviewed **exact** route key `cluster + registry mint + USDC mint + venue + program + pool`, an audited quote/context and runtime freshness; this is **not authorization, guaranteed executability or a submitted order**. No user-supplied pool/program/fee recipient. Current ready-context count is zero. Benten reason codes cover invalid asset, wrong genesis, pool mismatch/paused, missing liquidity, RPC failure, stale quote and unsafe unsigned payload. User rejection, onchain failure and submission unknown belong to the external execution owner; Benten may report them only through a separately reviewed, source-verified readback, not its route state.
